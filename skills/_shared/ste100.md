# Writing standard — ASD-STE100 (Simplified Technical English)

> **Reference-only.** Not a skill. All English text that the SDD pipeline writes must agree with
> ASD-STE100 (Issue 9 or later). Every skill and every agent points to this file. The
> `artifact_language` switch sets the language of the prose → [`artifact-language.md`](./artifact-language.md).
> This file sets how the English prose is written.

## Scope

Use ASD-STE100 for this English text:

- Chat replies, `AskUserQuestion` text and the stage-handoff block → [`handoff.md`](./handoff.md).
- Pipeline artifacts: spec, SAD, ADR, data model, test plan, task files, review and fix records,
  changelog and PR body.
- Agent reports and findings.
- Code comments, docstrings and commit messages that a skill or an agent writes.
- The plugin docs: `SKILL.md` files, references, templates, agents, README and CONTRIBUTING.

Do not use ASD-STE100 for:

- Prose that is not in English (for example, `artifact_language: uk`). An English text in the
  same artifact must obey this standard.
- Code identifiers, commands, file paths, configuration keys and values, and error messages.
- Machine tokens that the pipeline parses → the «Never translate» list in
  [`artifact-language.md`](./artifact-language.md). Do not change these tokens.
- Template headings. Keep each heading verbatim from its template.
- Quoted text: the words of the user, a document or a tool output.

## Precedence

This standard controls the prose style. It does not change the structure of a skill. Keep the
templates, headings, sections, step order, output shapes and literal tokens that a skill or an
agent specifies. Write the text in those sections in ASD-STE100.

## Word rules

1. Use only the approved words of the ASD-STE100 dictionary, with their approved meaning and
   part of speech.
2. You can use technical names and technical verbs from the domain. Examples: "API", "endpoint",
   "migration", "commit", "deploy", "refactor".
3. Use the same word for the same thing each time. Do not use a synonym.
4. Use American English spelling.
5. Do not use more than 3 nouns in a noun cluster. Break a longer cluster with a preposition.
6. Do not use slang, idioms, contractions or phrasal verbs that are not approved.
7. Use these approved replacements:

| Do not write | Write |
|---|---|
| utilize, leverage | use |
| ensure, verify | make sure |
| perform, accomplish, carry out | do |
| require | must have, necessary |
| provide | give, supply |
| obtain, fetch (in prose) | get |
| initiate, commence | start |
| terminate | stop |
| modify | change |
| prior to | before |
| following, subsequent to | after |
| in order to | to |
| approximately | about |
| sufficient | enough |
| additional | more, other |
| attempt | try |
| assist, facilitate | help |
| eliminate | remove |
| indicate | show |
| remain | stay |

## Verb rules

1. Use only these verb forms: infinitive, imperative, simple present, simple past, future
   ("will" + verb), and the past participle as an adjective.
2. Do not use the "-ing" form as a verb. You can use it in a technical name ("routing table").
3. Use the active voice in procedures. Use the passive voice only in descriptive text, and only
   when it is necessary.
4. Use an action verb, not a noun made from a verb. Write "Install the package", not "Do the
   installation of the package".

## Sentence rules

1. Procedural sentences: 20 words or fewer. Descriptive sentences: 25 words or fewer.
2. Write instructions in the imperative.
3. Write one instruction in one sentence. Two actions in one sentence are permitted only when
   you do them at the same time.
4. Put a condition before the instruction. Write "If the test fails, stop", not "Stop if the
   test fails".
5. Use articles ("the", "a", "an") and demonstratives ("this", "these").
6. Write only one topic in one sentence.

## Paragraph rules

1. Start a descriptive paragraph with a topic sentence.
2. Write one topic in one paragraph, with 6 sentences or fewer.
3. Use vertical lists and tables for sequences, options and data.
4. Use a numbered list for steps that the reader must do in sequence.

## Warnings and cautions

1. Start a warning or a caution with a short, clear command.
2. Then give the risk in one short sentence.
3. Example: "Do not run this migration on production. It deletes all rows in the table."

## Self-check

Before you write an artifact, a report, a commit message or a reply, examine the English text:

1. Are all words approved words or technical names?
2. Are the sentences short enough?
3. Are the instructions in the imperative, with one instruction in each sentence?
4. Are there no noun clusters with more than 3 nouns?
5. Is each term the same term each time?

If an answer is "no", correct the text before you write it. This check is part of the
structural self-check of each skill → [`self-check.md`](./self-check.md).

## Subagents

When a skill dispatches a subagent, the dispatch prompt tells the subagent to write its report
in ASD-STE100. Each file in `agents/` also contains the core rules, because a subagent does not
read this file.
